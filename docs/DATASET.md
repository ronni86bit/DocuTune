# Dataset Documentation

## Overview

DocuTune uses a **fully synthetic, deterministic, locally generated** dataset. No real
people's resumes, no personal data, no paid APIs, no external LLMs. The canonical
generator is `docutune/data/generator.py`; rendering lives in `docutune/data/renderer.py`.

- `DATASET_VERSION = "1.0"`, `SCHEMA_VERSION = "1.0"`, seed **42**
- Default size: **600 examples** — 450 train / 75 validation / 75 test (configurable)
- Files: `data/splits/{train,validation,test}.jsonl`, combined copy in
  `data/processed/all_examples.jsonl`, fingerprint in `data/dataset_manifest.json`
  (counts, template map, distributions, SHA-256 of each split file)
- Data license: same as the project (synthetic content generated by this repository)

## Generation Strategy

1. **Canonical record first.** A structured record is sampled from seeded pools
   (names, companies, universities, cities, titles, skills, certifications, projects,
   responsibility templates). Career timelines are constructed as consecutive
   non-overlapping segments with realistic durations; education precedes work.
2. **Rendering second.** The record is rendered into messy resume text by one of 12
   templates. The renderer changes *how* the record is written, never *what* is written —
   the canonical record is the gold label by construction.
3. **Independence.** Every example uses its own RNG derived from
   `(seed, split, template, index)` via pure integer arithmetic
   (`docutune/seed.py::derive_seed`), so the dataset is byte-identical across runs and
   platforms and cannot leak by construction (the validator still checks explicitly).

## JSONL Format

```json
{
  "id": "resume_000001",
  "text": "rendered resume text",
  "target": { ...canonical record, schema v1.0... },
  "metadata": {
    "template_id": "template_07",
    "template_name": "Experience-first resume",
    "difficulty": "medium",
    "split": "train",
    "seed": 42,
    "schema_version": "1.0",
    "dataset_version": "1.0"
  }
}
```

## Rendering Templates (12)

| # | Name | Split | Base difficulty | Distinct features |
|---|---|---|---|---|
| 01 | Traditional | train | easy | classic order, `-` bullets, "June 2022 - Present" |
| 02 | Compact | train | easy | inline uppercase headings, abbr months |
| 03 | Paragraph-heavy | train | medium | responsibilities/education as prose sentences |
| 04 | Bullet-heavy | train | easy | `•` bullets, `MM/YYYY` dates |
| 05 | Minimal | train | easy | no email/phone/summary/projects/certs |
| 06 | Modern | train | medium | uppercase headings, `|` skills, `–` ranges |
| 07 | Experience-first | train | medium | reordered sections, mixed date formats |
| 08 | Education-first | train | medium | ISO dates, education first |
| 09 | Projects-first | validation | medium | projects first, "to" ranges |
| 10 | Skills-heavy | validation | medium | skills grouped into labelled paragraphs |
| 11 | Fragmented | **test** | hard | shuffled sections, mixed casing/bullets/present-words |
| 12 | Noisy formatting | **test** | hard | `###` headings, random blank lines/trailing spaces |

Varied dimensions: section order, heading synonyms (5 per section), bullet symbols,
date formats (`June 2022`, `Jun 2022`, `06/2022`, `2022-06`, `2022`), range separators
(`-`, `–`, `to`), present-words (`Present`, `Current`, `Now`, `Till Date`), contact-line
styles, education/project/cert formats, skills separators.

## Train/Validation/Test Split Methodology

The split is **template-based, not a random split**:

- train: templates 01–08 · validation: templates 09–10 · test: templates 11–12

This is a deliberate generalization probe: the test set's *rendering style* is absent
from training, so good test scores indicate the model learned the extraction task rather
than memorizing surface patterns. Every example is independently generated, and the
validator enforces: no duplicate text across splits (normalized comparison), no
duplicate canonical records across splits, and strict template/split assignment.

## Difficulty Levels

Each example is labeled `easy`/`medium`/`hard` from its template's base level plus
hardship factors: paragraph-embedded content, grouped skills, mixed date formats,
3+ missing optional fields, 10+ skills, 6+ responsibilities, 3+ jobs. Hard examples
remain realistic — the goal is realistic extraction difficulty, not gibberish.

## Realistic Missing Information

Examples randomly omit: email, phone, location, summary, grades, projects,
certifications (template 05 omits most of these by design). Gold labels use
`null` / `[]` accordingly.

## Leakage Prevention

- Independent per-example RNG (see above)
- Cross-split duplicate-text and duplicate-record detection (validator)
- Template/split assignment checks (validator)
- Training code physically loads only `train.jsonl` / `validation.jsonl`;
  `configs/train.yaml` contains no reference to a test file

## Reproducibility

```bash
python scripts/generate_data.py --seed 42     # byte-identical output
python scripts/validate_data.py               # full integrity report
```

`data/dataset_manifest.json` records the seed, counts, template map, distributions and
the SHA-256 of every split file. `scripts/validate_data.py` (and the benchmark) fail
loudly if the data on disk does not match the expected contract.

## Limitations

- Synthetic language bias: templates and pools shape the vocabulary; real resumes differ
- 600 examples is small; it demonstrates methodology, not production readiness
- Held-out templates narrow, but do not eliminate, style overfitting
- The gold label is the canonical record: extraction is "correct" relative to the
  generator's conventions (e.g. date normalization), which the prompt states explicitly
